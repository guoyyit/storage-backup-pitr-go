# storage-backup-pitr-go

本地可运行的持久化键值存储与备份恢复服务。写入持久化在本地磁盘，进程崩溃后恢复到最后一个一致状态；支持全量备份、增量备份与任意历史提交时间点恢复（PITR），全部能力可在本地单机复现与验证。

## 构建与运行

```bash
go build ./...
go test ./...          # 运行全部自动化测试

# 启动服务
go run ./cmd/kvserver -addr 127.0.0.1:8080 -data data/engine -backup data/backup
```

### HTTP API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `PUT` | `/kv/{key}` | 写入（请求体为值），返回 `{"seq": n}` |
| `GET` | `/kv/{key}` | 读取最新已提交值 |
| `DELETE` | `/kv/{key}` | 删除，返回 `{"seq": n}` |
| `POST` | `/backup/full` | 全量备份，开启新链，返回 `{"chain": id}` |
| `POST` | `/backup/incr?chain={id}` | 增量备份（`chain` 缺省为最新链） |
| `GET` | `/chains` | 列出全部备份链及段清单 |
| `POST` | `/restore` | 恢复，body: `{"target_dir","chain_id","point_in_time","to_seq"}` |
| `POST` | `/validate?chain={id}` | 校验链完整性，损坏时返回具体段名 |
| `POST` | `/retention` | 执行回收，body: `{"retain_count","retain_age_sec"}` |

### 命令行可配置项

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `-addr` | `127.0.0.1:8080` | HTTP 监听地址 |
| `-data` | `data/engine` | 引擎数据目录 |
| `-backup` | `data/backup` | 备份存储目录 |
| `-sync-writes` | `true` | 每次提交 fsync，保证崩溃不丢已提交数据 |
| `-snapshot-threshold` | `10000` | 引擎每多少条提交做一次快照并归档 WAL |

## 架构

```
cmd/kvserver        HTTP 服务
internal/engine     存储引擎：WAL + Memtable + 快照
internal/backup     备份链管理：全量/增量/恢复/校验/保留
```

**存储引擎**：写操作在写锁内串行提交，先追加 WAL（每帧带 CRC32），再应用内存状态。每个提交获得单调递增的 `Seq` 与单调不减的提交时间（UnixNano，与 Seq 严格同序）。WAL 超过阈值后写快照并归档旧 WAL 段。崩溃后重放 WAL，尾部撕裂帧被安全截断，恢复到最后一个完整提交。

**备份链**：每次全量备份开启一条新链，增量备份以段的形式追加到链上：

```
backup/chains/<chain-id>/
  manifest.json                 # 链清单：段序列 + sha256 + Seq 区间
  snapshot-....snap             # 全量段（一致点快照）
  incr-<from>-<to>.segment      # 增量段（WAL 帧格式，逐条 CRC）
```

## 一致点的定义

**一致点 = 某个已提交 Seq 时刻的完整状态。** 引擎的写操作串行提交，内存状态恰好反映 `Seq ≤ S` 的全部已提交写。全量备份在读锁内原子地捕获 `(S, 状态)`，因此备份内容恰好等于 Seq `S` 的已提交状态：备份期间并发写入要么已包含在 `S` 内（完整生效），要么在 `S` 之后（完全不出现），不存在撕裂——从备份恢复出的状态不丢写、不重写。

## 恢复语义

- 恢复目标由 `point_in_time`（RFC3339）或 `to_seq` 指定，同时给出时取更严者；缺省恢复到链尖。
- 恢复结果 = 全量段基线 + 按序回放增量段中 `seq ≤ to_seq 且 commit_time ≤ point_in_time` 的记录。**回放严格截断在目标点，该点之后的写入不出现在恢复结果中。**
- 恢复写入独立的 `target_dir`（拒绝写入运行中引擎目录、备份目录及被无关内容占用的目录），不触碰源备份与备份链。
- 恢复先写入 `target_dir.restore-tmp/` 临时目录，自检通过后原子 rename。**中断后重新执行的结果与一次成功恢复完全一致**，部分写入只可能残留在临时目录，重试时清除；对同一目标重复同一恢复为幂等成功。
- 恢复出的目录是完整引擎目录，可直接用 `-data` 指向它启动新实例继续服务。

## 备份完整性与损坏检测

每个段文件带整体 SHA256（记录在 manifest），快照逐条 CRC32 + 全文件 CRC，增量段逐帧 CRC32。`POST /validate` 或恢复前校验会逐段核验，任何损坏（比特翻转、截断、丢失）都返回 `CorruptionError`，错误中包含链 ID 与具体段文件名。校验只认真实损坏，不误伤完好数据；损坏链不会被静默恢复出错误状态。

## 保留策略

`RetentionPolicy` 支持两种条件，同时设置时满足任一即保留，都为零表示不回收：

- `retain_count`：仅保留最新 N 条链；
- `retain_age_sec`：仅保留创建时间在该时长内的链。

回收以整条链为单位，保留范围内的链的可恢复性不受影响。回收与备份/恢复并发时结果确定：正在被恢复引用的链本轮跳过，删除在链写锁内完成。备份完成后引擎侧已被覆盖的归档 WAL 自动回收，长期运行下已归档数据总量可控。

## 并发模型

- 备份/恢复期间读写服务持续可用：全量备份只在读锁内拷贝内存状态，增量备份直接读取 WAL 文件，均不阻塞读写（仅快照拷贝瞬间占用读锁）。
- 多个备份任务并发执行时各自开启独立链，链间目录与清单完全隔离，互不污染；同一链上的增量追加串行化。
- 引擎崩溃恢复：WAL 尾部撕裂帧被识别并截断，恢复到最后一个完整提交（测试覆盖 `kill -9` 场景）。
